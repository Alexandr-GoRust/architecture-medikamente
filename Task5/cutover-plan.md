# Task 5. Cutover-план миграции «Медикаменте»

## 1. Анализ ситуации и выбор стратегии

**Что мигрируем:** ручные процессы на Excel/сканах/почте и 1С (файловый режим)
→ целевая платформа: портал записи клиентов, портал ресепшена, CRM, платёжный
шлюз, интеграция с лабораторией (API), аналитическое хранилище.

**Ограничения кейса:**
- медицинские данные нельзя «просто выключить» — клиника работает каждый день;
- нет ни автоматических тестов, ни формальных контрактов старых процессов
  (Excel — это «коллективные знания» сотрудников), поэтому полное поведение
  старой системы неизвестно заранее;
- команда к миграциям не привыкла (3 IT-специалиста), часть процессов ведут
  немедицинские сотрудники (кассиры, ресепшен) — нужна простота переключения;
- рост нагрузки ожидается кратно (филиалы) — новое решение обязано работать
  до масштабирования, а не «после»;
- 152-ФЗ: переключение не должно создавать период, когда ПДн обрабатываются
  вне согласованного регламента.

**Сравнение вариантов:**

| Критерий | High-Level Design | Parallel Run | Branch by Abstraction |
|---|---|---|---|
| Гарантия функциональной полноты до переключения | Низкая: редкие процессы всплывают после перехода | **Высокая: сверка выходов двух систем ловит пропуски** | Средняя: перенос по компонентам, но старых компонентов нет — переносить нечего |
| Цена ошибки для живого бизнеса | Максимальная | **Минимальная: старая система обслуживает, пока новая доказывает себя** | Средняя |
| Требует «монолита» с API для подмены реализаций | — | — | **Да, а у нас его нет** (Excel/1С-файлы) |
| Сложность | Низкая (по сути — проектирование) | Средняя (сверки, двойной ввод на переходный период) | Высокая |
| Покрывает организационные/ручные процессы | Частично | **Да: сверка журнала Excel и записей в CRM** | Нет |

**Выбор: Parallel Run.** Обоснование: старая «система» — ручные журналы и 1С —
остаётся источником истины, пока новая CRM/порталы параллельно обрабатывают те
же заявки; сверка записей, оплат и расписания выявляет расхождения (включая
редкие/специфические процессы, которые никто не задокументировал) до полного
переключения. Branch by Abstraction неприменим — нет кодовой базы с абстракциями
для подмены; чистый High-Level Design не снижает риск пропуска функциональности.

Ограничения Parallel Run, которые принимаем управленчески: двойной ввод данных
на переходный период (нагрузка на ресепшен/кассиров ~1–2 месяца), риск
рассинхронизации копий (лечится автоматическими ночными сверками и «треугольником»
ответственности: владелец старого процесса + владелец нового + бизнес-аналитик).

## 2. Cutover-план (поэтапный)

| Этап | Описание действия | Ключевые задачи | Ответственные | Время/Сроки | Риски и меры по снижению |
|---|---|---|---|---|---|
| 0. Подготовка | Зафиксировать As-Is и объём миграции | Инвентаризация всех журналов/файлов Excel и сканов; карта потоков данных (Task1); выбрать критичные процессы: запись → оплата → медкарта → лаборатория; обучение команд новому порталу | Техдиректор (архитектор), бизнес-аналитик | 2 нед. | «Слепые зоны» — неучтённые процессы → сбор коллективных знаний: интервью/наблюдение за ресепшеном и кассирами; всё фиксируем в DFD |
| 1. Освоение стека и ролей | Новые сервисы развернуты, доступы по RBAC/ABAC | Развернуть CRM/порталы/шлюз (стенд = прод-конфигурация); категории данных по доменам; роли: ресепшен, кассир, врач, бухгалтер, IT | Администратор сети, техдиректор | 2 нед. | Нехватка экспертизы в команде → обучение на малом контуре + документация runbook; привлечение вендора/подрядчика при необходимости |
| 2. Наполнение и перенос данных | Исторические данные → новая система | Импорт пациентов (минимально необходимый набор — Data Minimization); сканы медкарт — во вложения с шифрованием; проверка целостности выборочных записей | Бизнес-аналитик, ресепшен | 2 нед. | Утечка при переносе ПДн → перенос по внутреннему каналу (TLS), журнал операций, разовая выгрузка без копий на АРМ |
| 3. Параллельная работа | Обе системы живут: Excel/1С — источник истины, новая — «тень» | Клиентские заявки дублируются в CRM; сверки: записи/день, оплаты/день, расписание/неделю; фиксируем расхождения в реестре и разбираем каждое | Ресепшен, кассиры, бизнес-аналитик | 4–6 нед. | Двойной ввод утомляет, сотрудники «саботируют» новую систему → прозрачная коммуникация «зачем», сокращение дублирования до критичных полей, помощь на местах |
| 4. Переключение трафика по процессам | Постепенно: сначала запись через портал (клиенты), затем оплата, затем медкарты | Маршрутизация: новые записи клиентов сразу в CRM, ресепшен видит обе системы; старый журнал — только чтение | Техдиректор, ресепшен | 2–3 нед. (по 1 нед. на процесс) | Просадка качества приёма → каждый процесс переключается только после недели нулевых критичных расхождений |
| 5. Мониторинг и стабилизация | Метрики нового решения под контролем | Дашборд: доля записей через портал, ошибки оплат, время ответа, инциденты доступа; еженедельный разбор; горячая линия для сотрудников | IT-отдел (все трое) | 2 нед. | Скрытые отказы не видны → алерты (мониторинг + аудит доступа), утренняя сверка остатков |
| 6. Отключение старых контуров | Excel-журналы и файловая 1С — в архив | Архивирование с шифрованием, установка сроков хранения и удаления (152-ФЗ); 1С:Бух остаётся до отдельного проекта (бухучёт не меняем в этой волне) | Техдиректор, бухгалтерия | 1 нед. | Случайное удаление нужного → архив + бэкап, окно отката 30 дней |

**Критические моменты:** (а) первый день приёма после переключения записи —
дежурство IT на месте; (б) инкассация/ККМ при переключении оплаты — сверка чеков
каждую смену; (в) доступ врачей к медкартам — проверка RBAC «свои пациенты»
до и после переключения.

## 3. План отката (rollback)

1. Вернуть маршрутизацию заявок на старый процесс (Excel-журнал остаётся
   «живым» до конца этапа 6 — это условие отката);
2. Досинхронизировать записи/оплаты, сделанные в новой системе, в старый журнал
   (ручная выверка за период инцидента);
3. Разбор причины, повторная попытка переключения не раньше чем через неделю
   после устранения.

Триггер отката: > 2 критичных расхождения за день на процессе ИЛИ недоступность
новой системы > 30 минут в рабочие часы.

## 4. Риски стратегии и распределение ролей

| Риск | Мера | Ответственный |
|---|---|---|
| Рассинхронизация данных двух систем | Автосверка (ночная) + «треугольник»: владелец старого процесса, владелец нового, бизнес-аналитик | Бизнес-аналитик |
| Двойной ввод → ошибки и усталость | Дублируем только критичные поля; сокращаем период параллельности по метрикам | Техдиректор |
| Сопротивление сотрудников | Обучение, понятные инструкции, поддержка на местах, показ пользы (меньше рутины) | Техдиректор + руководители отделов |
| Редкие процессы не перенесены | Реестр расхождений параллельного периода — каждый случай до закрытия переключения не завершается | Бизнес-аналитик |
| Утечка ПДн в переходный период | Перенос по TLS, минимум копий, аудит доступа, DLP на АРМ | Администратор сети |
| Недостаток ресурсов IT (3 человека) | Приоритет процессов, подрядчик на пиковые недели, автоматизация сверок | Техдиректор |

Роли: техдиректор — владелец миграции и архитектуры; администратор сети —
инфраструктура, доступы, безопасность; бизнес-аналитик — сверка, обучение,
реестр расхождений; ресепшен/кассиры — операционная работа в обеих системах;
бухгалтерия — приёмка оплат; руководство — эскалация и приёмка этапов.
