# Task 4. Узкие места при миграции — отчёт

Диаграмма Исикавы: `ishikawa.drawio` (категории: Инфраструктура, Программное
обеспечение, Данные, Интеграция, Персонал, Процессы).

Контекст: миграция ручных процессов (Excel/сканы/почта, 1С в файловом режиме,
сервер Windows в офисе) на микросервисную архитектуру (порталы, CRM, платёжный
шлюз, API лаборатории, аналитика). Ревью-фокус: системность и глубина
проработки рисков **снижения производительности**.

## Категории и возможные проблемы (по костям диаграммы)

| Категория | Проблемы (причины узких мест) |
|---|---|
| **Инфраструктура** | один сервер в офисе без резервирования; Kubernetes-кластера нет на старте — всё на одной ноде; медленные диски под БД; каналы к филиалам без VPN/QoS |
| **Программное обеспечение** | 1С в файловом режиме — блокировки файла БД при конкурентном доступе; Excel-обработка грузит всё в память; в новых сервисах забыты пагинация и индексы; монолитные релизы — долгий откат |
| **Данные** | двойной учёт (Excel + 1С) — расхождения и повторные сверки; миллионы мелких сканов JPG/PDF на общем диске; нет партиционирования истории; «грязные» данные → повторные перезагрузки |
| **Интеграция** | OLE-мост ККМ↔1С однопоточный и хрупкий; обмен с лабораторией по почте; синхронные сервис↔сервис вызовы без таймаутов; нет формальных контрактов API |
| **Персонал** | 3 IT-специалиста — single point of failure; незнание нового стека (K8s/Postgres); критические знания только в головах (коллективные знания); сопротивление отказу от Excel |
| **Процессы** | ручная сверка при параллельном запуске; нет регламента отката; нагрузочное тестирование отсутствует до запуска; приоритизация задач без метрик |

## Рекомендации и приоритеты (устранение узких мест)

| # | Мера | Закрывает | Приоритет | Обоснование |
|---|------|-----------|-----------|-------------|
| 1 | Нагрузочное тестирование новых сервисов ДО переключения (профили: запись, оплата, чтение карты) + smoke после каждого релиза | ПО, Процессы | **P0** | дёшево, ловит отсутствие индексов/пагинации до прода |
| 2 | Индексы/пагинация/кеше в CRM и ЭМК; партиционирование истории по месяцам | ПО, Данные | **P0** | самые частые операции — запись и чтение карты |
| 3 | Перевод 1С из файлового режима в клиент-серверный до старта миграции платежей | ПО, Интеграция | **P1** | файловые блокировки уронят оплату при конкуренции |
| 4 | Два узла Kubernetes + Postgres с репликой (в т.ч. в другом помещении), SSD под БД | Инфраструктура | **P1** | доступность и производительность БД; RTO/RPO |
| 5 | VPN/QoS до филиалов; замена OLE-моста ККМ на API-интеграцию через шлюз | Инфраструктура, Интеграция | **P1** | платёжный поток не должен зависеть от хрупкого моста |
| 6 | Асинхронные интеграции (очередь/события) + контракты API (OpenAPI) с таймаутами и rate limit | Интеграция | **P2** | развязывает сервисы, поток не блокируется соседом |
| 7 | Скрипты автоматической сверки при Parallel Run (ночные батчи вместо ручных) | Данные, Процессы | **P2** | ускоряет миграцию и убирает человеческие ошибки |
| 8 | Обучение команды (K8s/Postgres) + документирование коллективных знаний (runbook) + подрядчик на пиковые недели | Персонал | **P2** | снижает риск ошибок и время реакции |
| 9 | Регламент отката миграции с триггерами (см. Task5) и «дежурство на месте» в первые дни | Процессы | **P2** | управляемость инцидентов при переключении |

Критерий расстановки приоритетов: (1) влияние на живой бизнес-поток
(запись/оплата/приём), (2) вероятность срабатывания при миграции,
(3) стоимость меры. P0 выполняется до любого переключения потока;
P1 — до расширения на филиалы; P2 — в ходе параллельного периода.
